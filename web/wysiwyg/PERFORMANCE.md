# 编辑器性能契约

## 桌面端十秒卡顿：已定位的根因

2026-09-06 使用同一份 244,229 字节、4,752 个映射节点的专项文档，在原生 Rust **调试构建**中测量：旧实现仅计算 UTF-16 光标映射耗时 **9.69 秒**；修改后完整 Markdown → AST（包含映射）耗时 **123.7 ms**。这是解析阶段的单次本机实测，不是端到端打开耗时。

旧实现对每个节点执行 `source[..byte_offset].encode_utf16().count()`，重复扫描文档前缀。现收集并排序所需边界，一遍扫描正文完成转换，复杂度由 O(节点数 × 文档长度) 降为 O(文档长度 + 边界数 log 边界数)。Unicode 回归验证映射兼容。

同时修正桌面 UI 路径：

- 文件读取、AST 构建/序列化、字数统计和源码预览生成使用两个固定后台工作线程；异步函数本身不被视为后台线程。
- 字数和预览以 Markdown 内容为依赖，布局/工具栏重绘不重新解析。资源任务取消后，尚未开始的后台工作会跳过。
- 移除首次挂载时重复的 AST 同步。打开对话框显示读取状态并允许取消，过期加载结果不再覆盖当前文档。
- 所见即所得和源码视图在加载超过 1 秒后才显示官方 Dioxus Dialog；短任务不会闪烁弹窗。挂载脚本先让浏览器绘制界面，再创建编辑 DOM。关闭提示只让任务转入后台，完成状态仍由实际任务控制。

复现算法对比（特意运行一次旧扫描算法，测试本身约需十秒）：

```sh
cargo test --offline benchmark_long_document_mapping -- --ignored --nocapture
```

后台线程路径适用于原生目标；WASM 目前保留同步回退，需要单独的 Worker 集成，不能用桌面结果宣称网页线程也已隔离。

## 执行模型

Rust 负责文档、AST、存储等业务逻辑；ProseMirror、CodeMirror、公式 DOM 和浏览器排版运行在 WebView 主线程。Rust 不会自动消除 JavaScript 的重复解析或同步 DOM 布局。

- **输入路径**只提交 ProseMirror 事务。分页异步执行，每个文档版本最多一个活动任务。新事务、字体/图片变化或销毁取消旧任务；提交前检查文档身份和页面尺寸签名。选区事务和分页自己的装饰事务不触发重新测量。
- **测量路径**使用一个无插件、不可编辑的连续排版工作区，共享不可变文档节点，通过 ProseMirror DOM reconciliation 更新。不会临时移除正在编辑的正文中的分页间隔，也不会逐键复制整棵 DOM。
- **测量缓存**按不可变文本块和排版样式存储行几何。只在真正选为分页边界的行上二分查找字符位置，并缓存相对于段落的结果。段落移动不会使相对位置失效；宽度、字体、图片等改变会使相关缓存失效。
- **协作调度**以 6 ms / 128 次操作为让出检查点，使用真正的任务边界而非微任务。该预算不能抢占单次浏览器原生布局、单个公式渲染或 ProseMirror 原子事务，因此不是硬实时保证。
- **分页外观**只为视口附近创建页缝遮罩，滚动仅刷新遮罩。正文、选区、表格结构和撤销历史仍由同一个编辑器管理；分页不改写文档模型。
- **源码投影**按不可变顶层块缓存序列化和位置映射，未变块不重复解析。源码桥接将快照差异压缩为最小 UTF-16 安全修改范围，保留 CodeMirror 的未变区间。源码语法扩展仅在源码视图挂载期间启用；共享历史始终保留。
- **公式**合并同一节点的待渲染请求，在任务片段中渲染，销毁后取消；分页等待公式队列，但旧分页版本可独立取消等待。

## 可重复验收

```sh
npm run test:editor
npm run test:pagination-browser
npm run test:pagination-performance
cargo test --offline
```

浏览器测试使用本机 Chromium 的真实时钟、原生动画帧和 CDP pipe，不使用虚拟时钟。`CHROMIUM` 可指定可执行文件。每个场景输出临时 PNG 和 JSON 报告路径。应单独运行性能测试，避免与构建或其他浏览器测试争抢 CPU。

正确性覆盖嵌套列表/引用、跨页长段落、多行表格、混合公式与代码、页缝遮挡、列宽、视口中部/尾部滚动、纸张尺寸及无缝模式切换，以及公式输入与源码往返。

性能使用 `examples/long-paragraph-test/document.md` 的完整 244,229 字节正文和图片；测试纸张高度为 120 mm，以产生约 273 页压力。通过真实共享文档会话测试短段落 40 次输入、最长 9,520 字符段落 20 次输入、主动取消旧任务、源码视图挂载/修改以及重新进入所见即所得。

自动门槛：空闲/选区变化不重新测量；首次 Range 读取少于 30,000；旧版本确实取消；内容和模式往返一致；增量序列化/索引数量不超过输入事务数；单次输入事务低于 50 ms、输入间定时器额外延迟低于 100 ms。时间门槛是本地回归上限，不能解释为所有设备上的帧率保证。

`mountMs` 只计同步构造；`longestByPhase` 同时记录浏览器报告的长任务，不能用前者替代首帧性能。浏览器测试中的 `reference-parser` 是构造 Rust AST 输入的测试适配器；实际产品由 Rust 提供 AST。测试没有测量 IPC、Rust 解析、文件 I/O 或桌面 WebKit 的耗时。

## 仍需独立验收的边界

- 正文尚未整体虚拟化：活动编辑 DOM 和测量 DOM 均随文档规模增长。只有页缝遮罩按视口裁剪。首轮字体整形、布局和源码视图构造仍可能产生超过 50 ms 的长任务。
- 缓存粒度是文本块/顶层源码块。修改一个极长段落或一个庞大的顶层列表，仍需处理整个受影响块；拼接完整 Markdown 和最终分页打包也仍与文档规模有关。
- 单行表格高于整页时，需要单元格跨页拆分模型。专项文档保留这一压力用例；普通多行表格通过不代表此边界已解决。
- 原生输入法、桌面 WebKit、PDF 导出和百万字符文档需要各自的交互/性能验证；Chromium 自动化不能替代它们。
